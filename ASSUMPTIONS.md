# Assumptions & Design Decisions

## Technology choices

| Choice | Reason |
|---|---|
| **Node.js + Express 5 (JavaScript, ES modules)** | Simple, widely known, and the code reads clearly. Express 5 forwards errors from `async` handlers to the error middleware automatically. |
| **PostgreSQL** | Real ACID transactions, row-level locks (`SELECT … FOR UPDATE`), exact `NUMERIC` type for money, and `CHECK`/`UNIQUE`/`FOREIGN KEY` constraints. These are the core needs of a ledger. |
| **`pg` (node-postgres) with plain SQL** instead of an ORM | Locking, conditional updates and transaction boundaries are explicit and easy to review. There is no code-generation step, which keeps setup on Windows, macOS and Linux simple. |
| **Zod** | Declarative request validation that produces clear, per-field error messages. |
| **SQL migration files + a tiny runner** (`npm run db:migrate`) | The schema is versioned in `migrations/` and recorded in a `schema_migrations` table. Running it again is safe. |
| **Node's built-in test runner + Supertest** | No extra test framework configuration. Tests run end to end against a real PostgreSQL database. |

## How data integrity is guaranteed

### Atomicity
Every credit, debit and transfer runs inside **one database transaction** (`withTransaction` in `src/config/database.js`). The balance update and the transaction insert are committed together. If anything fails, `ROLLBACK` discards both. A test forces a failure after the debit is written and verifies that nothing persists.

### Concurrency
1. The account row is locked with `SELECT … FOR UPDATE` before anything else happens. A second request for the same account waits until the first one commits.
2. The balance update is conditional: `UPDATE … SET balance = balance + $delta WHERE id = $1 AND balance + $delta >= 0`. A debit therefore can never overdraw, even in theory.
3. Transfers lock both accounts **in a fixed order (sorted by id)**, so two opposite transfers (A→B and B→A) cannot deadlock.

The tests verify this behaviour:
- 20 simultaneous debits of 10 against a balance of 100 → exactly 10 succeed and the balance ends at 0.
- 10 simultaneous submissions of the same `reference_id` → exactly 1 is created.
- 20 simultaneous opposite transfers → all succeed and the total money is conserved.

### Database constraints (defence in depth)
The database enforces these rules even if application code had a bug:
- `CHECK (balance >= 0)` on accounts.
- `CHECK (amount > 0)` on transactions.
- `UNIQUE (account_id, reference_id)`: duplicate protection is enforced by the database itself.
- `FOREIGN KEY account_id → accounts(id)` with `ON DELETE RESTRICT`.
- `CHECK` constraints that reject a blank name or blank reference.
- An enum type for `credit`/`debit`.
- A `BEFORE UPDATE OR DELETE` **trigger on `transactions`** that raises an error, so transaction rows are immutable even outside the API.

### Balance consistency
The balance is stored on the account (fast reads) and is only ever changed in the same database transaction that inserts the matching transaction row. The invariant `balance == SUM(credits) − SUM(debits)` therefore always holds, and the tests assert it after concurrent mixed traffic.

## Assumptions about the requirements

1. **Account IDs and transaction IDs are UUIDs** generated by PostgreSQL (`gen_random_uuid()`).
   - A malformed id returns `400 INVALID_ACCOUNT_ID`.
   - A well-formed id that doesn't exist returns `404 ACCOUNT_NOT_FOUND`.
2. **The client cannot set `balance`, `id` or `created_at`.** Sending them returns `400` with a clear message, rather than silently ignoring them, so the client learns the field has no effect. All unknown fields are rejected the same way.
3. **Amounts** must be JSON numbers greater than 0 with at most 2 decimal places, up to 1,000,000,000 per transaction.
   - Amounts are stored as `NUMERIC(18,2)` and all arithmetic happens in PostgreSQL, so there are no floating-point errors (0.10 + 0.20 = 0.30 is tested).
   - Responses return amounts as JSON numbers.
   - Numeric strings like `"50"` are rejected to avoid ambiguity.
4. **There is a single currency.** No currency field is stored.
5. **Duplicate `reference_id` handling:**
   - A repeated `reference_id` on the same account returns **`409 Conflict`** (`DUPLICATE_TRANSACTION`) and includes the **original transaction** in `error.details.transaction`, so a client retrying a request can see what was recorded.
   - This applies even if the repeated request has a different type or amount. The reference identifies the transaction.
   - The duplicate check runs before the balance check, so a retried debit reports "duplicate" rather than "insufficient balance".
   - `reference_id` is trimmed, so `" INV-1 "` and `"INV-1"` are the same reference.
6. **Insufficient balance returns `422 Unprocessable Entity`.** The request is well-formed but violates a business rule. A debit that equals the full balance is allowed (the balance becomes 0).
7. **`description` is optional.** It is stored as `null` when omitted, with a maximum of 500 characters. `name` is limited to 255 characters and `reference_id` to 100.
8. **Pagination:**
   - `page` defaults to 1 and `limit` defaults to 10, with a maximum `limit` of 100.
   - Non-integer, zero, negative or repeated values return `400 INVALID_PAGINATION`.
   - Requesting a page beyond the last returns an empty `data` array with correct totals rather than an error.
   - The response also includes `has_next_page` and `has_previous_page`.
9. **Sorting** is `created_at DESC`, with `id DESC` as a deterministic tie-breaker. `created_at` uses `clock_timestamp()`, so rows inserted within the same database transaction (such as the two transfer legs) still get distinct times.
10. **Immutability:**
    - There are no update or delete endpoints for transactions.
    - `PUT`/`PATCH`/`DELETE` on a transaction URL returns `405` with `Allow: GET`, which explains the rule instead of returning a generic 404.
    - Accounts also cannot be deleted through the API, which keeps history intact.
11. **Transfers (bonus):**
    - Each transfer is recorded as two normal transactions (a debit on the source and a credit on the destination) that share a `transfer_id`. Both legs therefore appear in each account's history and count toward each balance.
    - Both legs use the request's `reference_id`, so it must be unused on **both** accounts; otherwise the API returns `409`.
    - Transferring to the same account returns `400`.
12. **Validation error codes:** when all invalid fields belong to one category, a specific code is returned (`INVALID_AMOUNT`, `INVALID_TRANSACTION_TYPE`, `INVALID_PAGINATION` or `INVALID_ACCOUNT_ID`). Otherwise the code is `VALIDATION_ERROR`. `details` always lists every problem.
13. **No authentication or authorization** is in scope for this assignment.

## Out of scope / possible improvements
- Authentication, and per-user ownership of accounts.
- An `Idempotency-Key` header that returns the original `201` response on retry, rather than `409`.
- Cursor-based pagination for very large histories (offset pagination is simple and fine at this scale).
- Request logging and metrics, rate limiting, and a Dockerfile/docker-compose setup.
- A periodic reconciliation job comparing the stored balance with the transaction sum.
